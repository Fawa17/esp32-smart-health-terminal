# 智能健康监护终端 · 项目说明

> 一个从 STM32F103 + 外挂 ESP8266（AT 指令上云）双芯片方案，整体迁移并重构到 ESP32-S3 单芯片的居家健康监护设备。
>
> 固件版本 **1.5.3** ｜ 二进制 **1 228 896 B**（1.23 MB，2 MB app 分区余 41%）｜ 17 个组件、约 1.1 万行 C

---

## 1. 这个设备能干什么

面向独居老人的居家监护终端，**四路生理指标 + 本地触摸屏 + 云端看板 + 远程升级**：

| 能力 | 说明 | 数据来源 |
|---|---|---|
| 心率 / 血氧 | 100 Hz 采样，2 秒窗口出一次结果，无效时上报 `null` 而非 0 | MAX30102（I2C 0x57） |
| 步数 / 跌倒 | 矢量模长 + 重力基线 + 峰谷状态机，跌倒三阶段确认 800 ms | MPU6050（I2C 0x68） |
| 体表温度 | 16 次 ADC 均值 → eFuse 标定转 mV → 分压反算 R → Beta 公式 → EMA | NTC 热敏（ADC1_CH3） |
| 时间 | SNTP 联网校时，断电后从 NVS 恢复，不依赖外置 RTC | SNTP + NVS |
| 本地界面 | LVGL 四页（时钟 / 数据 / 设置 / 告警），手势翻页，30 s 息屏，按键唤醒 | ST7789 兼容面板 240×296 |
| 云端 | 2 s 周期上报、远程阈值下发、告警推送、OTA 升级 | esp-mqtt |

## 2. 硬件

### 2.1 主控与屏幕

| 部件 | 型号 | 关键参数 |
|---|---|---|
| 主控 | ESP32-S3 | 双核 Xtensa LX7 @240 MHz，16 MB Flash，8 MB **八线 PSRAM** |
| 屏幕 | TK020F1131 | 240×296 IPS，**驱动 IC = TK0134（不是 ST7789）**，SPI 接口，8 针二合一（SPI 显示 + I2C 触摸） |
| 触摸 | CST816S | I2C 地址 0x15，`IRQ`/`RST` **未引到排针**，只能轮询 |

### 2.2 接线

| 外设 | 信号 | ESP32-S3 | 备注 |
|---|---|---|---|
| 公共 I2C | SDA / SCL | **GPIO8 / GPIO9** | 400 kHz，三器件共用 |
| 屏幕 | SCK / MOSI / CS / DC | GPIO12 / GPIO11 / GPIO10 / GPIO13 | 40 MHz，无 RES 脚（靠软复位） |
| MAX30102 | INT | GPIO21 | 未接则走轮询 + 盲读降级 |
| NTC | AO | GPIO4 | ADC1_CH3 |
| DS1302 | CLK / DAT / RST | GPIO5 / GPIO6 / GPIO7 | **当前该模块判定为硬件故障**，已可降级 |
| 按键 | KEY | GPIO14 | 低有效 + 内部上拉。**不要用 GPIO0**（strapping，按着开机进下载模式） |

> I2C 上三个从机地址不冲突：0x15（触摸）/ 0x57（MAX30102）/ 0x68（MPU6050）。
> 屏幕引脚必须避开 26–32（Flash）、33–37（八线 PSRAM）、19/20（USB）、0/3/45/46（strapping）。

## 3. 软件架构

### 3.1 四层解耦

```
┌────────────────────────────────────────────────────────┐
│  网络层  net_app ─ wifi_mgr ─ mqtt_cli ─ ota_app        │  建链 / 上报 / 下行 / OTA
├────────────────────────────────────────────────────────┤
│  业务层  hr_algo（心率血氧） · 计步/跌倒状态机 · 告警判定  │  只做算法与判断
│           ui_lvgl（LVGL 四页 + 手势 + 息屏）             │
├────────────────────────────────────────────────────────┤
│  系统层  app_data（快照）· watchdog · sys_pm             │  调度 / 并发 / 掉电 / 崩溃
│           time_keeper · crash_log                        │
├────────────────────────────────────────────────────────┤
│  感知层  bsp_i2c · mpu6050 · max30102 · ntc_temp        │  把物理量变成结构体
│           ds1302 · touch · display                       │
└────────────────────────────────────────────────────────┘
```

**层间只通过结构体与回调交互，依赖方向单向**，三条证据（面试可直接举）：

1. `sys_pm` 的 `CMakeLists.txt` 只有 `PRIV_REQUIRES driver esp_timer`，它**不认识** `display` 和 `touch`，息屏时要关屏、要停触摸，是通过 `sys_pm_hooks_t { on_sleep, on_wake }` 让 `main.c` 去接的。
2. `net_app` 不知道 DS1302 存在。SNTP 对时成功后不直接写 RTC，而是回调 `net_time_cb_t`，由 `main.c` 的 `app_rtc_sync()` 决定写哪儿。
3. `ui_lvgl_set_data()` 只做一次结构体拷贝（`portMUX` 保护），所有 LVGL 调用收敛在单一 ui 任务，**LVGL 不是线程安全的**，跨任务直接调会随机崩。

### 3.3 任务与调度

| 任务 | 周期 | 优先级 | 核 | 栈 | 说明 |
|---|---|---|---|---|---|
| `wifi` / `esp_timer` / `lwIP` | — | 23 / 22 / 18 | 0 | 内置 | **应用任务优先级必须 ≤ 17** |
| `wdt_mon` | 200 ms | 17 | 0 | 3072 | 槽位心跳监控 |
| `max30102` | 10 ms | 15 | 1 | 3072 | 100 Hz 采样 |
| `mpu6050` | 40 ms | 14 | 1 | 3072 | 25 Hz 采样 |
| `hr_algo` | 事件 | 13 | 1 | 6144 | 窗口满即算 |
| `net_uplink` | 2 s | 8 | 0 | 4096 | 上报 |
| `sys_pm` | 事件+200 ms | 6 | 1 | 3072 | 息屏 / 唤醒 |
| `touch` | 20 ms | 5 | 1 | 3072 | 50 Hz 轮询 |
| `ui` | ~30 ms | 4 | 1 | 6144 | `lv_timer_handler` |
| `ntc_temp` | 2 s | 4 | 1 | 3072 | 温度 |
| `main` | 500 ms | 1 | 0 | 3584 | 汇总 / 刷屏 / 存储 |

> **两个 FreeRTOS 语义陷阱**：IDF 的 `xTaskCreate` 栈深**单位是字节**（STM32 是字）；`app_main` 返回后主任务会被删除，必须自己 `while(1)` 或建任务。

## 4. 数据流

```
传感器任务 ──成功才打卡──► watchdog（槽位超时先恢复、3 次才复位）
    │
    ├─► app_data_publish()  ← 单写者，portMUX 保护，整结构体拷贝
    │        │
    │        ├─► ui_lvgl_set_data()  → ui 任务 → LVGL 脏区重绘 → flush_cb
    │        │                                             → PSRAM 帧缓冲
    │        │                                             → SPI-DMA 8 行分块
    │        └─► build_params() → esp-mqtt publish（2 s）
    │                                    │
    └────────────────────────────────────┴─► 云端看板（Socket.IO + Chart.js）
                                              ▲
                            下行：阈值配置 / OTA 查询 / 重启
```

**`app_data` 的作用**：早期 UI 直接调四个模块的 `get_xxx()`，五次独立读取之间数据会变，拼出的帧可能「上一秒的心率 + 这一秒的血氧」。改成单写多读快照后，一帧数据永远是同一时刻的。

## 5. 六个实际问题

### 5.1 屏幕全屏「负片」，反色开关怎么调都无效

- **现象**：颜色像照片反色，深底变亮、纯白变纯黑，`DISP_INVERT_COLOR` / `DISP_BGR_ORDER` / `DISP_SWAP_BYTES` 三个开关任意组合都无效。
- **定位**：色块自检（画红绿蓝白黑黄六条 + 字母）→ 白块显示成黑 = 仍在反色。拿到厂家参考工程后才发现 **驱动 IC 是 TK0134，不是标称的 ST7789**。
- **根因**：`esp_lcd_new_panel_st7789()` 会灌一整套 ST7789 命令，其中 `0xB0~0xB4` 在 ST7789 是伽马，而 **TK0134 的 `0xB0` 是 RAMCTRL（显存访问控制）**，显存读写方式被写坏，所以怎么调反色都没用。
- **修复**：丢掉官方 panel 驱动，只留 `esp_lcd_panel_io_spi`，按手册自写 6 条初始化（`0x3A=0x05` / `0x36` MADCTL / `0x21` INVON / `0x11` / `0x29`）与 `CASET / RASET / RAMWR` 刷屏时序。

### 5.2 OTA 升到一半板子自己重启

- **现象**：进度 4% → 8% → 12% 后无故重启，复位记录显示「卡死的槽位 #0（任务名 mpu）」。
- **根因**：`esp_ota_write` 每擦 4 KB 扇区要 20~50 ms，期间**两核 cache 全关、中断被推迟**；1.6 MB 固件要擦 389 次，40 ms 周期的采集任务必然轮不到 CPU → 被自己的看门狗判成卡死。
- **修复**：`watchdog_set_pause_check(ota_app_in_progress)`，升级期间把**所有槽位**的心跳计时归零并跳过判定，任务本身不再被误判；同时 `ui_lvgl_set_paused(true)` 停渲染（cache 关闭时 LCD DMA 读 PSRAM 会 panic）。
- **副产品**：升级期间的传感器「离线」日志是误报，成功后自动清零。

### 5.3 心率永远偏低、血氧虚高

- **根因**：算法移植自 Maxim AN6409，逐行对照后发现 **7 处缺陷**，最致命的是算 AC 分量时用了红光峰值下标去索引红外序列（`an_x[n_y_dc_max_idx]` 应为 `n_x_dc_max_idx`），导致 R 值系统性偏大。
- **附带**：提前 return 时不写输出参数（调用方拿到未初始化栈值）、谷点数组有空洞、平均间隔代替中位数、int32 乘积溢出。
- **修复**：全部修正，并新增灌注指数与峰间隔离散度闸门，剔除拉腕与运动伪影。

### 5.4 MAX30102「永远不出数」

- **现象**：寄存器配置全对（`MODE=0x03`、`SPO2=0x27`、片内温度正常），但 FIFO 写指针 `WR/RD` 恒为 0，一个样本都读不到。
- **定位**：对比 STM32 原版发现唯一差异，原版**从不看指针**，直接读 6 字节 FIFO。而这颗兼容片的 `WR/RD` 寄存器恒读 0，但 `OVF_COUNTER` 会涨（溢出只可能由写入造成）。
- **修复**：检测到「指针恒 0 但溢出计数 > 0」→ 自动切**盲读模式**（10 ms 读 1 个样本），指针恢复可用后自动退出。修复后实测 心率 78 / 血氧 96 / 片内温度 29.9 ℃。

### 5.5 LVGL 数字显示成「1 + 乱码方框」

- **根因**：`lv_label_set_text_fmt(lbl, "%.1f", t)`，**LVGL 自带的 `lv_snprintf` 默认不支持 `%f`**。
- **修复**：改定点拼接 `fmt_temp()`：`snprintf("%s%d.%d", sign, a/10, a%10)`，不依赖 LVGL 的 printf。

### 5.6 中文显示成方框（两种原因，判据不同）

| 现象 | 原因 | 修法 |
|---|---|---|
| 方框**和字号一样大**、整行全方 | 该标签用了 Montserrat（纯西文） | 换 `FONT_CJK` |
| 方框**和正文一样大**、只有个别字方 | 字库缺这个字 | 重跑字库生成脚本 |

- 字库方案：`lv_font_conv` + `C:\Windows\Fonts\Deng.ttf`，**扫描源码字符串字面量自动收集汉字**（当前 306 字），替代 LVGL 自带 1.3 MB 的 CJK 字库。
- 顺带一个问题：`lv_snprintf` 不支持 `%f`，`-Os` 下 `snprintf` 还会触发 `-Werror=format-truncation`（按 int 最坏位数推算），要先把结果拼进局部小缓冲再拷贝。

## 6. 可靠性体系

| 层 | 机制 | 效果 |
|---|---|---|
| 任务级 | 应用心跳槽位 + 硬件 TWDT | 超时先调恢复回调（重装 I2C），连续 3 次才复位 |
| 器件级 | `WHO_AM_I` / `PART_ID` / FIFO 指针变化 | 连续 5 次失败判掉线，屏幕转橙 + 云端上报 `fault` 位图，插回 5 s 自愈 |
| 总线级 | 9 个 SCL 脉冲 + STOP | 从机死锁后无需断电自愈 |
| 系统级 | `RTC_NOINIT_ATTR` 记录复位原因/死机任务名 | 重启后打印「上次是哪个任务卡的」 |
| 崩溃级 | panic → coredump 分区（PC / 任务名 / 调用栈） | `idf.py coredump-info` 直接定位到代码行 |
| 升级级 | 双分区 + `PENDING_VERIFY` 状态机 | 60 s 内没连上云端就自动回滚 |
| 时间级 | SNTP 校时 + NVS 持久化（5 分钟节流） | 断电重启时间不倒退，不依赖外置 RTC |

## 8. 资源占用

| 项 | 数值 |
|---|---|
| 固件 | 1 228 896 B（1.23 MB），app 分区余 **41%** |
| Flash Code (.text) | ~775 KB |
| DIRAM | 149 KB / 334 KB（44%） |
| IRAM | 16 KB / 16 KB（**100%，余量为 0**） |
| PSRAM 帧缓冲 | 240×296×2 = 141.6 KB |
| LCD 刷屏 | 28 ms/整帧（40 MHz SPI，理论上限 ~35 fps） |
| I2C 总线占用 | < 8%（按事务字节/周期计算） |
| 上电到 MQTT 建链 | 5.3 s（WiFi 3 s + MQTT 1 s） |

> **IRAM 100% 的含义**：这里的 16 KB 是 `iram0_0_seg`（`IRAM_ATTR` 代码 + 中断向量），不是全部 512 KB SRAM。现在刚好装满，**再加一个 `IRAM_ATTR` 函数就会链接失败**（报 `region 'iram0_0_seg' overflowed`）。工程里只有两处 `IRAM_ATTR`（MAX30102 中断、LCD 传输完成回调），真需要腾空间时先删它们。

## 9. 已知限制

| 限制 | 现状 | 影响 |
|---|---|---|
| **DS1302 不可用** | 三次自检结果互不一致（RAM 回环 0x4B/0x00、秒值倒退），判定为模块/接线层问题 | 已用「系统时间优先 + NVS 持久化」兜住，功能不受影响 |
| 触摸无硬件中断 | 模块 IRQ/RST 未引出，只能 50 Hz 轮询 | 功耗略高，响应 20 ms 级，够用 |
| 无 Light Sleep | 只做了面板级省电（DISPOFF + SLPIN） | 手动 `esp_light_sleep_start()` 会断 WiFi/DHCP，正确做法是 `CONFIG_PM_ENABLE` + `esp_pm_configure()` 自动轻睡 |
| 心率未做精度标定 | 只有「能出数」，没有 MAE 数据 | 简历里不能写误差指标 |
| 无自动化测试 | 全部靠实机 + 串口日志 | 无回归保护 |

## 10. 后续优化（按性价比排序）

1. **MAX30102 批读**：现在 10 ms 读 1 个样本 = 100 次 I2C 事务/秒；改 100 ms 读 10 个，事务数 −90%，顺带消掉 10 ms 硬节拍与芯片 RC 漂移。
2. **I2C 相位错峰**：MPU 40 ms 与 MAX 10 ms 整除，每 40 ms 必撞车；改 37 ms 或错开 5 ms。
3. **UI 行级脏区刷新**：现在按 LVGL 脏区传整行区间，可进一步只传变化行，28 ms → 8 ms 量级。
4. **测心率血氧误差**：与指夹血氧仪对比 20 组，出 MAE，这是简历里唯一还没填的数字。
5. **OTA 分块续传**：现在断了从头来，用 HTTP Range 续传。
6. **栈水位实测**：3072 / 6144 / 8192 都是估的，用 `uxTaskGetStackHighWaterMark` 实测后下调。
